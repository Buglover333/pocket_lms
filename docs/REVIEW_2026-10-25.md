# Исправления после комментариев Никиты, 25 октября 2026

Исправления интегрированы поверх актуальной ветки `endpoints` (база 596878a). Базовый архив сверён побайтово с этой версией. Существующий CRUD-слой и четыре DELETE-маршрута сохранены. Ветка main не изменяется.

## Принятые решения

- Удалить `get_dashboard` из проектных материалов. В коде его уже нет. Главная использует отдельные запросы курсов, модулей, заданий и сдач. Для главной со всеми дедлайнами нескольких курсов текущий `get_calendar(course_id)` вызывается отдельно по каждому курсу.
- Публикация уже реализуется `PATCH /update_material` или `PATCH /update_assignment` с `is_published`. Отдельные POST publish не нужны. Получение опубликованного контента — GET. Не заменять изменяющую операцию на GET.
- `GET /get_module_data(module_id)` вызывается до редактирования модуля. Название `get_module` из комментария — уточнение действия, а не необходимость создавать второй дублирующий путь.
- `GET /get_submissions(assignment_id, student_id?)`: по умолчанию свои сдачи указанного задания. Чужого студента может выбрать преподаватель именно этого курса. Результат включает доступную студенту командную работу. Получение конкретной сдачи с вложениями оставлено отдельно: оно нужно экрану проверки и не заменяет список.
- Единственный запрос чтения профиля — `GET /get_user_info?user_id=...` (ID совпадает с токеном). Дублирующий `GET /get_settings` удалён; frontend ещё отсутствует. Минимальные «настройки» = профиль: имя и фамилия редактируются, email отображается без редактирования. Темы интерфейса, уведомления и смена пароля в эту реализацию не включены. Предложение состава настроек требует продуктового согласования.

## Что означает active

В именах HTTP-эндпоинтов слова active нет. В БД:

| Поле | Смысл | Создание / изменение |
|---|---|---|
| users.is_active | Аккаунт действует | register создаёт TRUE; внутренний CRUD delete_user меняет на FALSE. Публичного HTTP-удаления аккаунта нет. update_settings не может менять это поле. |
| discipline_members.status | Участие в курсе: active / invited / left | accept_invitation создаёт active; внутренние CRUD add/update/remove_discipline_member работают с членством. Отдельный HTTP-запрос управления статусом не реализован. |

У материала и задания используется is_published; у курса — status draft/published/archived. Это разные состояния и их нельзя объединять под одним active.

## Сделано в локальном коде

- Общие проверки доступа к курсу, материалу, заданию, сдаче и файлу.
- Участник другого курса не получает материалы, задания, календарь и команды.
- Черновики скрыты от студентов, персональные задания доступны назначенным исполнителям.
- Проверка сдачи: студент должен состоять в курсе; команда должна соответствовать курсу и членству. Нельзя сдавать от чужого имени или присваивать себе graded/returned.
- Список сдач ограничен выбранным студентом; чужие сдачи и вложения закрыты. Командные сдачи и оценки доступны активным участникам команды.
- Имена можно редактировать; передача password_hash, email, is_admin/is_active в публичные настройки отклоняется. Внутренняя CRUD-модель отделена от публичного запроса.
- Загруженные вложения проверяются по владельцу, завершённости загрузки и привязке. Привязка к сдаче выполняется в транзакции с блокировкой строк файлов.
- grade_submission принимает только graded и обязательный конечный балл от 0 до max_score; возврат выполняет return_submission.
- get_course_data содержит доступный список материалов; get_materials нужен для отдельного обновления этого списка. Интерфейсу не требуется вызывать оба подряд. Журнал скрывает задания из неопубликованных материалов и задания без персонального назначения.
- S3: сервер резервирует уникальный ключ; клиент не выбирает bucket/key. Подписанная POST-форма ограничена размером и MIME-типом. Подтверждение проверяет HEAD объекта. Ссылка скачивания выдаётся после проверки доступа и действует 300 секунд.
- Удалено повторное объявление таблицы users из схемы для новых баз. Разрушающие миграции на существующей БД не выполнялись.

## Файлы и S3: конкретный сценарий

1. POST /create_file_upload — JSON: file_name, file_type, mime_type, size_bytes; при необходимости lesson_id. Возвращает file_id, upload_url, fields, expires_in.
2. Браузер отправляет multipart/form-data непосредственно в S3: возвращённые fields + поле file с содержимым. Это запрос к хранилищу, а не JSON с байтами в LMS.
3. POST /complete_file_upload?file_id=... — сервер сверяет размер и MIME через S3 HEAD и отмечает файл ready.
4. POST /submit_work — JSON с assignment_id, submitted_by, answer_text, file_ids. Файлы для сдачи сначала загружаются без submission_id; затем сервер привязывает их к созданной сдаче. Для resubmit_work можно передать новые file_ids.
5. GET /get_file — метаданные после проверки доступа.
6. GET /get_file_download — внешняя ссылка или временная подписанная ссылка S3, после проверки доступа.

Старый POST /upload_file теперь описан как регистрация внешней HTTP-ссылки. Он не загружает байты в S3 и не принимает поддельные S3 bucket/key/status. Удаление /delete_file удаляет запись БД; физическая очистка S3 требует отдельной фоновой процедуры и пока не реализована. Не обещать физическое удаление объекта этим запросом.

Для S3 нужны S3_BUCKET, регион, IAM-права на конкретный bucket и рабочие credentials/роль окружения. Реальные ключи в проект не добавлялись.

## Сверка юзер-флоу и БД: оставшиеся разрывы

| Требование схемы | Что есть в текущей БД / коде | Что ещё требуется |
|---|---|---|
| Модуль: версия, тематический план, результаты, пререквизиты, даты | modules: title, description, curator_id | Согласовать структуру и добавить поля/связи и миграцию. Нельзя заявлять, что create_module уже сохраняет весь список из флоу. |
| Курс: часы, темы, контрольные точки, даты начала | disciplines содержит описание, тип, ends_at; lessons/assignments частично покрывают темы и задания | Уточнить модель учебного плана и контрольных мероприятий. |
| Публикация по таймеру | Только is_published; нет publish_at и планировщика | Оставлено как нереализованное требование. Для реализации нужны миграция и механизм отложенной публикации, а не только поле в JSON. |
| Доступ к материалу выбранным студентам или команде | lessons доступны на уровне курса | Нет таблицы получателей материалов; нужны правила и таблица/связи. |
| Персональное назначение задания | assignment_targets и CRUD есть | HTTP create/update_assignment ещё не принимает список targets: соответствующий контракт/маршрут нужно добавить. В тестах назначения создаются непосредственно в тестовой БД. |
| Приглашение преподавателя и приглашение в модуль | Код курса и accept_invitation с ролью student | Роль и область приглашения не моделируются отдельно; текущий код не выполнять как приглашение преподавателя. |
| Команда | Команда и одно team_id у участника курса | Нет полноценного HTTP-управления составом, истории состава; get/update_group меняют данные команды, а не автоматически её участников. |
| Итоговая оценка | Оценки по попыткам в submissions | Нет отдельной итоговой оценки, правил выбора попытки и формулы. get_final_grades/update_final_grade в коде отсутствуют. |
| Первичная статистика | Данные сдач есть, готового запроса статистики нет | Согласовать метрики; не считать старый get_course_statistics реализованным. |
| Контакты | get_members возвращает профили участников курса | Отдельный get_contacts не нужен для этого состава данных; группировку по курсам делает интерфейс. |
| Новый аккаунт создаёт курс / модуль | Текущий код позволяет назначить себя автором/куратором | Продуктово подтвердить, может ли любой пользователь создавать курс/модуль, или нужны выданные администратором права. Выбор роли на экране не решает этот вопрос. |
| Номер попытки / повторная сдача | Начальная сдача считает MAX+1; resubmit обновляет запись | Нужно согласовать хранение истории попыток и ограничения параллельных сдач. Текущая правка не меняет эту модель. |

Эти разрывы зафиксированы, но не замаскированы выдуманными полями API. Их реализация требует выбора продуктового поведения и изменения БД. Настоящая end-to-end проверка S3 не выполнялась: хранилище и credentials не предоставлены; протокол проверен с подменённым S3-адаптером.

## Проверка и передача

База проверки: отдельная `pocket_lms_api_test_review_20261025` в тестовом PostgreSQL 16 на localhost:55433. Рабочие данные не изменялись. Тесты исходного архива и новые объектные проверки запускаются командой из TEST_RESULTS_REVIEW.md.

HTTP-контракт с типами, JSON-примерами и ответами: API_CONTRACT_REVIEW.md + openapi.json. Примеры генерируются из моделей; это синтетические данные, не реальные аккаунты.

Реальные S3 upload/download требуют настройки и отдельной проверки bucket, IAM и CORS. Продуктовые разрывы из таблицы выше остаются открытыми. Изменения коммитятся в endpoints; push и слияние в main не входят в эту операцию.
